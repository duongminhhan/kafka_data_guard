# Kế hoạch refactor cho UAT - 2026-07-28

## Trạng thái triển khai

Đã triển khai trong source ngày 2026-07-28:

- chuẩn hóa package runtime về `src` và build image trực tiếp từ source hiện tại;
- gọi `spGetKafkaGuardTopicConfig` theo `ConnectorName`;
- parse/validate `ListCDCTopic` và Oracle credential;
- map sanitized topic schema về Oracle owner thật;
- cache cấu hình theo connector;
- tạo Oracle client pool một connection riêng theo `ConfigID`;
- xử lý đồng bộ, toàn app chỉ có một abandoned transaction đang chạy;
- giữ `poll`, xử lý, `commit` và `seek` trên cùng consumer thread;
- chỉ commit request sau khi remediation và Kafka publish thành công.

Đã xác minh: unit test, compile, SQL migration chạy lặp, HTTP health,
stored procedure lookup, topic mapping và Oracle pool initialization.

Consumer chỉ poll transaction kế tiếp sau khi transaction hiện tại xử lý và commit
offset xong. UAT chỉ chạy một replica để không phát sinh xử lý song song giữa instance.

## Mục tiêu

- Cho phép một service tiếp nhận request từ nhiều Kafka Connect connector.
- Định tuyến mỗi connector tới đúng Oracle server thông qua `ConfigID`.
- Xử lý tuần tự toàn cục, không phụ thuộc connector hoặc Oracle server.
- Giữ hệ thống nhẹ bằng Python, không bổ sung Kafka Streams, DLQ hoặc bảng chống duplicate.
- App chỉ đọc Oracle và phát repair message lên Kafka, không ghi dữ liệu vào database nguồn hoặc đích.

## Cấu hình nguồn

App đọc cấu hình từ Microsoft SQL Server:

```text
KafkaGuardTopic
    ID
    ConnectorName
    ListCDCTopic
    ConfigID
    CreatedAt
    UpdatedAt
```

Ý nghĩa:

- `ConnectorName`: khóa dùng để tìm cấu hình khi nhận abandoned transaction.
- `ListCDCTopic`: chuỗi CSV chứa các CDC topic được phép phát repair.
- `ConfigID`: khóa ngoại tới `dbo.ETLConfiguration.ETLConfigurationID`.
- `UpdatedAt`: chỉ phục vụ audit tại bảng; app không đọc field này từ stored procedure.

Mỗi connector chỉ có một cấu hình hiệu lực. `ConnectorName` phải có unique constraint.

App dùng bảng cấu hình hiện hữu:

```text
ETLConfiguration
    ETLConfigurationID
    ConfigurationFilter
    QueueName
    ConfiguredDriver
    ConfiguredValue
    Description
```

- `ConfiguredDriver`: driver/loại database; phải nhận diện được Oracle.
- `ConfiguredValue`: chứa Oracle JDBC credential.
- App không sử dụng hoặc tạo thêm bảng `KafkaGuardConfig`.

### Contract lấy cấu hình runtime

Sau khi lấy được `ConnectorName` từ log abandoned, app gọi:

```sql
EXEC [dbo].[spGetKafkaGuardTopicConfig]
    @ConnectorName = :connector_name;
```

Stored procedure trả về tối thiểu:

```text
ConnectorName
ListCDCTopic
ConfigID
DatabaseCredential
```

Nếu procedure không trả row hoặc trả nhiều hơn một row, request phải fail trước khi
tạo Oracle connection. Loại database được validate trực tiếp từ protocol
`jdbc:oracle:thin:@//` trong `DatabaseCredential`.

### Parse CDC topic

`ListCDCTopic` là chuỗi CSV, ví dụ:

```text
oracle_remediation_poc.C__CDCUSER.PRODUCT,oracle_remediation_poc.C__CDCUSER.ITEM
```

App phải giữ nguyên topic đầy đủ để publish repair message, đồng thời tách thông tin
dùng cho câu SQL nguồn từ phải sang trái:

```python
topic_prefix, topic_schema, table_name = topic_name.rsplit(".", 2)
```

Kết quả ví dụ:

```text
topic_prefix = oracle_remediation_poc
topic_schema = C__CDCUSER
table_name   = PRODUCT
```

Không được dùng `split(".")` rồi lấy vị trí cố định từ trái vì topic prefix có thể chứa
dấu chấm. Topic không có đủ ba phần phải bị reject.

`C__CDCUSER` là schema token đã được sanitize để dùng trong Kafka topic, không nhất
thiết là Oracle owner thật. Với ví dụ hiện tại:

```text
Kafka topic schema: C__CDCUSER
Oracle owner:        C##CDCUSER
```

Không được áp dụng chung quy tắc thay mọi `__` thành `##`, vì tên schema hợp lệ có thể
thực sự chứa dấu gạch dưới. App phải map topic schema về Oracle owner bằng metadata
connector đã cache, ưu tiên `table.include.list`. Nếu connector chỉ đọc schema của
chính database user, username lấy từ credential có thể được dùng làm owner sau khi đã
đối chiếu table thuộc `ListCDCTopic`.

Kết quả parse được lưu thành:

```text
TopicBinding
    full_topic
    topic_prefix
    topic_schema
    oracle_owner
    table_name
```

Các câu SQL LogMiner, metadata và source SELECT dùng `oracle_owner.table_name`; Kafka
publisher vẫn dùng `full_topic`.

### Parse Oracle credential

`DatabaseCredential` được procedure lấy từ
`ETLConfiguration.ConfiguredValue`, theo format:

```text
jdbc:oracle:thin:@//;{host}:{port};{database};{username};{password};{connection_type}
```

Ví dụ đã che password:

```text
jdbc:oracle:thin:@//;localhost:1521;ORCLCDB;C##CDCUSER;***;normal_type
```

Thứ tự field:

```text
0 = jdbc:oracle:thin:@//
1 = host:port
2 = database/service name
3 = username
4 = password
5 = connection type
```

Với cấu hình hiện tại:

```text
database/service = ORCLCDB
username         = C##CDCUSER
password         = field thứ 5 trong chuỗi
connection type  = normal_type
```

Parser phải:

- tách đúng sáu phần và reject chuỗi thiếu hoặc dư field;
- kiểm tra protocol là `jdbc:oracle:thin:@//`;
- kiểm tra `host`, `port`, database, username và password không rỗng;
- chỉ chấp nhận connection type nằm trong whitelist;
- dựng DSN cho `python-oracledb` theo dạng `{host}:{port}/{database}`;
- không log chuỗi gốc, username/password hoặc DSN chứa credential;
- xóa password khỏi exception context và metrics label.

Trên UAT phải lưu hostname Oracle thực tế có thể truy cập từ app. App dùng trực tiếp
hostname trong `ConfiguredValue`, không tự đổi `localhost` hoặc áp dụng alias theo môi
trường.

## Luồng xử lý sau refactor

1. Webhook nhận log abandoned.
2. Bypass ngay request có `0 events`.
3. Đẩy request hợp lệ vào Kafka request topic.
4. Consumer lấy `ConnectorName` từ request.
5. Gọi `spGetKafkaGuardTopicConfig` bằng `ConnectorName`.
6. Parse `ListCDCTopic` thành các `TopicBinding`.
7. Parse `DatabaseCredential` thành Oracle connection config.
8. Chọn Oracle client pool tương ứng với `ConfigID`.
9. Chạy LogMiner và Flashback trên đúng Oracle database.
10. Chỉ giữ table thuộc danh sách `TopicBinding`.
11. SELECT nguồn bằng Oracle owner và table name đã map.
12. Publish repair message vào đúng `full_topic`.
13. Chỉ commit Kafka request sau khi publish thành công.

Nếu không tìm thấy connector, `ConfigID`, Oracle config hoặc topic không nằm trong
whitelist, request phải fail rõ ràng và không được truy vấn database khác.

## Thay đổi code

### Configuration repository

- Gọi `spGetKafkaGuardTopicConfig` theo `ConnectorName`.
- Stored procedure join `KafkaGuardTopic.ConfigID` với
  `ETLConfiguration.ETLConfigurationID`.
- Không SELECT trực tiếp bảng credential từ application code.
- Parse và validate `ListCDCTopic` trước khi tạo Oracle connection.
- Parse credential bằng một model riêng, không truyền raw string xuyên suốt app.
- Không ghi credential ra application log.
- Validate `ListCDCTopic` là chuỗi CSV không rỗng và không có phần tử rỗng.

### Configuration cache

- Cache cấu hình theo `ConnectorName`.
- TTL ban đầu: 5 phút.
- Refresh khi cache TTL hết hạn.
- Không truy vấn SQL Server cho từng transaction.
- Cho phép xóa cache của một connector khi cần cập nhật khẩn cấp.

### Oracle client registry

Quản lý Oracle connection pool theo:

```text
ConfigID -> OracleClientPool
```

- Khởi tạo pool khi request đầu tiên tới.
- Tái sử dụng pool cho các connector dùng chung Oracle server.
- Đóng pool khi service shutdown.
- Có idle timeout để giải phóng pool không còn sử dụng.

### Phân luồng xử lý

- Chỉ có một consumer thread thực hiện remediation.
- Không dùng worker pool hoặc semaphore theo `ConfigID`.
- Mỗi Oracle client pool chỉ có một connection.
- Transaction hiện tại phải xử lý và commit offset xong trước transaction kế tiếp.

Ví dụ:

```text
Request 1 -> Server A
Request 2 -> Server B
Request 3 -> Server A
```

Thứ tự xử lý là Request 1, sau đó Request 2, cuối cùng Request 3.

Toàn bộ lifecycle sau phải chạy trên cùng một Oracle connection:

```text
ADD_LOGFILE
-> START_LOGMNR
-> SELECT V$LOGMNR_CONTENTS
-> END_LOGMNR
```

### Kafka consumer

- Webhook chỉ parse, bypass và enqueue; không query Oracle.
- Kafka key dùng `ConnectorName` hoặc `ConfigID` để định tuyến ổn định.
- Consumer xử lý trực tiếp một request, không chuyển sang worker queue.
- Không poll request mới trong lúc remediation đang chạy.
- Chỉ commit offset sau khi transaction được xử lý và publish thành công.
- Khi thất bại, request được retry theo cơ chế at-least-once hiện tại.
- Hệ thống chấp nhận repair message có thể bị phát trùng.

### Kafka Connect runtime config

- Cache runtime config theo `ConnectorName` với TTL 5 phút.
- Không gọi Kafka Connect REST API cho từng transaction.
- `ListCDCTopic` chỉ là whitelist, không thay thế các thuộc tính cần để dựng payload
  như topic prefix, PDB, converter schema, decimal mode và time precision.

  `ETLConfigurationID`.
- Khai báo ít nhất hai connector trỏ tới hai Oracle server khác nhau.
- Kiểm tra quyền Oracle của từng credential.
- Kiểm tra network từ app tới SQL Server, Kafka Connect, Kafka và từng Oracle server.

### Giai đoạn 2 - Refactor và kiểm thử offline

- Cài đặt configuration repository và cache.
- Cài đặt Oracle client registry.
- Cài đặt queue/semaphore theo `ConfigID`.
- Thêm timeout cho SQL Server, Kafka Connect và Oracle.
- Viết unit test cho stored procedure contract, topic parser, credential parser,
  routing, cache, whitelist và concurrency.
- Giữ nguyên business logic dựng event đã được kiểm chứng.

### Giai đoạn 3 - Smoke test UAT

- Chạy một transaction có event trên từng Oracle server.
- Chạy một transaction `0 events`.
- Kiểm tra đúng connector, `ConfigID`, source database và output topic.
- Kiểm tra prefix bị loại đúng và source SELECT dùng Oracle owner thật.
- Kiểm tra topic schema đã sanitize được map đúng về owner.
- Kiểm tra credential sai format bị reject trước khi mở connection.
- Kiểm tra app không thực thi DML trên Oracle.
- Kiểm tra request chỉ được commit sau khi repair message xuất hiện trên Kafka.

### Giai đoạn 4 - Test tuần tự

Chạy chuỗi request:

```text
A1, B1, A2, C1, B2
```

Kỳ vọng:

- Chỉ có một request ở trạng thái đang xử lý tại mọi thời điểm.
- A1 hoàn tất trước B1; B1 hoàn tất trước A2, tiếp tục theo thứ tự consumer nhận.
- Không dùng nhầm Oracle credential hoặc connection.
- Một Oracle server lỗi không làm dừng queue của server khác.

### Giai đoạn 5 - Test tải

- Gửi tối đa 185 log/giây với phần lớn là `0 events`.
- Xác nhận `0 events` được bypass trước khi vào Oracle queue.
- Đo queue depth, thời gian chờ, thời gian LogMiner và thời gian publish.
- Test riêng số lượng nhỏ transaction thực sự cần repair.
- Không đặt mục tiêu chạy 185 LogMiner transaction/giây.

### Giai đoạn 6 - Rollout

- Chạy đúng một app instance và một consumer thread.
- Theo dõi ít nhất một chu kỳ vận hành UAT.
- Chuẩn bị rollback về phiên bản single-Oracle hiện tại.

## Metrics và logging cần có

- Tổng request theo `ConnectorName` và `ConfigID`.
- Số request `0 events` được bypass.
- Số request completed, failed và retry.
- Queue depth và thời gian chờ theo `ConfigID`.
- Thời gian xử lý LogMiner/Flashback.
- Số repair message được publish.
- Số Oracle connection đang active.
- Lỗi config missing, credential, permission, archive/redo và Flashback.

Không log password, JDBC URL đầy đủ có credential, SQL bind value nhạy cảm hoặc
toàn bộ source row nếu không cần thiết.

- Không có request nào truy vấn sai Oracle server.

- Không dùng topic prefix hoặc sanitized schema token làm Oracle owner.

- Credential parser dựng đúng DSN, username và password nhưng không log các giá trị đó.
- Transaction `0 events` không tạo Oracle query.
- INSERT, UPDATE và DELETE được dựng đúng operation.
- Không phát một phần khi transaction không đủ redo hoặc metadata.
- App không ghi dữ liệu xuống Oracle nguồn hoặc database đích.
- Request lỗi được retry trước khi consumer tiếp tục request kế tiếp.
- Credential không xuất hiện trong log.
- Queue không tăng không giới hạn khi Oracle xử lý chậm.
